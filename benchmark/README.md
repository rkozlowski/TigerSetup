# TigerSetup installer-technology benchmark

A reproducible comparison of **TigerSetup 0.7.1**, **Inno Setup 7.1.0** and
**NSIS 3.12** packaging the same four real, open-source Windows applications,
plus a minimal no-payload installer per technology, measured statically on
the build machine and at runtime on TigerWinLab's clean Windows 11 baseline.
This is an experiment, not a TigerSetup feature: nothing here is consumed by
`crates/`, and the product under test is frozen for the duration of a
campaign — the 0.7.0 prototype run found a capability gap (explicit
registry locations) that became 0.7.1 *before* the campaign this
repository's [`report.md`](../report.md) is generated from.

The durable result is `report.md` at the repository root, generated by
`scripts/New-Report.ps1` from `results/*.json`. That campaign is frozen:
its results are never regenerated, and a later TigerSetup is measured
*against* it rather than by rewriting it — `report-0.9.0.md` in this
directory, generated by `scripts/New-ComparisonReport.ps1` from
`results/0.9.0/*.json`, is the first such campaign (see *A later campaign
against the frozen baseline* below). `report-0.10.0-broad.md` is a
different question on the same machinery: whether the four-application
findings generalize across the fifteen real payloads of the compression
spike's corpus, each packaged under one small common contract (see *The
broad-corpus campaign* below). Everything under `benchmark/` is the
reproducible machinery that produces those results — except
`compression-spike/`, a separate experiment with its own `README.md` and
report: the payload-compression spike (zstd vs LZMA2 for a solid payload)
that this benchmark's size finding motivated.

`downloads/`, `canonical/` and `artifacts/` are regenerated by the scripts and
never committed (`.gitignore`); `results/` and `report.md` are the durable,
committed evidence.

### What a campaign commits

A campaign produces two kinds of evidence, and they are kept apart.

**The compact record is committed.** `lab-results.json` carries one row per
installer and is self-sufficient: the installer it ran (SHA-256, bytes, the
tool version, matching `build.json`), the canonical inventory that decided
its payload verdict (`canonicalInventory`: the document's path under the
results root and that document's own SHA-256), the payload comparison as
counts plus the full path lists of whatever was missing, differing or extra,
the Add/Remove Programs registration, the package-owned state, the timings,
the engine span, the cleanup verdicts and the lab job ids. Beside it,
`corpus.json`, `canonical/<App>.json`, `toolchain.json`, `build.json`,
`determinism.json`, `campaign-notes.json`, the `<app>-installers.json`
records and the generated CSVs. That set regenerates the campaign's report
byte for byte and answers an audit without a VM.

**The raw lab evidence is not.** `results/<campaign>/lab/` holds what the lab
returned per row — the job documents (every installed file's path, size and
SHA-256, the guest environment, the health checks, the engine's whole event
stream), the session records, the VM states, the job folders and their logs.
For a row that passed, all of it is either the canonical inventory again or a
value the compact record already carries, forty-five times over: the broad
campaign's job documents alone are 21 MB, against 4.4 MB for everything the
campaign keeps. It stays on the build machine for as long as it is useful and
is gitignored
(`/benchmark/results/*/lab/`, `/benchmark/results/*/smoke/`). A row that
fails needs no exception: its mismatch lists, its exit codes, its job status
and its job ids are all in the compact record, and the raw documents those
point at are still on the machine that ran it.

The first campaign's `results/lab/` and the 0.9.0 campaign's
`results/0.9.0/lab/` predate this split. They are committed history and are
left alone.

## Reproducing the benchmark

```powershell
# 1. Toolchain (one-time, on the build machine): Inno Setup 7, NSIS 3.12, 7-Zip
winget install --id JRSoftware.InnoSetup.7
winget install --id NSIS.NSIS
winget install --id 7zip.7zip

# 2. TigerSetup release binaries (the frozen product under test)
cargo build --release

# 3. Acquire and verify the pinned application artifacts
pwsh -File benchmark\scripts\Acquire-Downloads.ps1

# 4. Extract and derive the canonical payloads + hash inventories
pwsh -File benchmark\scripts\New-CanonicalPayload.ps1

# 5. Build all 15 installers, record build times, measure them, record the toolchain
pwsh -File benchmark\scripts\Build-Installers.ps1

# 6. The TigerWinLab campaign: 12 rows, one lab session each, serial
pwsh -File benchmark\scripts\Invoke-BenchmarkLab.ps1

# 7. Regenerate report.md from results/*.json
pwsh -File benchmark\scripts\New-Report.ps1
```

A smoke test of one row before a campaign, into a results root of its own so
the campaign's data stays clean:

```powershell
pwsh -File benchmark\scripts\Invoke-BenchmarkLab.ps1 -OnlyRows WinMerge-NSIS `
    -ResultsRoot benchmark\results\smoke\lab -OutputJson benchmark\results\smoke\lab-results.json
```

## A later campaign against the frozen baseline

`report.md` is the first campaign and stays as it is. A later TigerSetup is
measured against it with the same payloads, definitions, baseline, contracts
and timing boundaries, into a results set of its own, and reported by a
second generator that keeps the two apart. The 0.9.0 campaign
(`report-0.9.0.md`, `results/0.9.0/`) is the template:

```powershell
# 0. The product under test: the committed release binaries (cargo build --release)

# 1. The canonical payloads on disk must be the bytes the inventories record
pwsh -File benchmark\scripts\Test-CanonicalPayload.ps1 -OutputJson benchmark\results\0.9.0\canonical-verification.json

# 2. All 15 installers again, on this host, serial, under the process-tree meter
pwsh -File benchmark\scripts\Build-Installers.ps1 -ArtifactsRoot benchmark\artifacts\0.9.0 -ResultsRoot benchmark\results\0.9.0

# 3. A smoke row, then the four TigerSetup rows on the clean baseline
pwsh -File benchmark\scripts\Invoke-BenchmarkLab.ps1 -OnlyTechnologies TigerSetup -OnlyRows WinMerge-TigerSetup `
    -ArtifactsRoot benchmark\artifacts\0.9.0 -ResultsRoot benchmark\results\0.9.0\smoke\lab `
    -OutputJson benchmark\results\0.9.0\smoke\lab-results.json -BuildJson benchmark\results\0.9.0\build.json -Fresh
pwsh -File benchmark\scripts\Invoke-BenchmarkLab.ps1 -OnlyTechnologies TigerSetup `
    -ArtifactsRoot benchmark\artifacts\0.9.0 -ResultsRoot benchmark\results\0.9.0\lab `
    -OutputJson benchmark\results\0.9.0\lab-results.json -BuildJson benchmark\results\0.9.0\build.json -Fresh

# 4. The comparison report
pwsh -File benchmark\scripts\New-ComparisonReport.ps1 -Campaign 0.9.0
```

What the later campaign measures that the first did not:

- **Every build's process tree.** `ProcessTreeMeter.psm1` starts the
  compiler suspended inside a Windows job object of its own and resumes
  it, so every process it creates is measured with it — NSIS's
  `makensis.exe` is a 2.5 KB launcher for `Bin\makensis.exe`. Wall clock
  runs until the job is empty; CPU time (user + kernel, exited processes
  included) and peak commit (`PeakJobMemoryUsed`, all processes together;
  `PeakProcessMemoryUsed`, the largest one) are the job's own kernel-
  maintained accounting, exact; peak working set is sampled every 20 ms
  (the largest sum of the processes' working sets in one sample, and the
  largest Windows-tracked per-process peak read while that process was
  alive) and can under-read a build shorter than a few samples — every
  record carries its sample count and the processes seen against the
  job's total, and the commit figures are the ones to trust for a build
  of milliseconds. Builds are serial; the technology order rotates between
  applications. The host (Windows build, CPU, memory, the repository's
  drive) is recorded in the campaign's `toolchain.json`.
- **The installed payload file by file.** The install job asks the guest
  reader for every installed file's SHA-256 (`inventoryHashes`), read after
  the timed command, and the row compares it with the canonical inventory:
  `payloadExact`, the files matched, missing and differing, and the
  `payloadExtras` the technology added under the install root. The first
  campaign compared counts and byte totals.
- **The engine inside the process lifetime.** A TigerSetup row brings the
  engine's log back and, with the guest's clock at the process's start and
  end, records the span from `run_started` to `run_finished` and what ran
  before and after it — the loader's share of the lifetime, measured.
- **Build identity on every row.** Each row records its installer's hash
  and the tool version from the campaign's `build.json`, and the campaign
  record names the builder and engine, so a runtime figure is tied to the
  bytes it measured.

The first campaign's scripts still run as before: `Build-Installers.ps1`
with no roots writes `artifacts/` and `results/`, and `New-Report.ps1`
regenerates `report.md` from them — though `results/` is now historical
evidence and is not rebuilt.

## The broad-corpus campaign

`report-0.10.0-broad.md` asks a different question of the same three
technologies: not how each fares under one application's real installer
contract, but how installer size, build cost, install and uninstall time,
payload fidelity and bookkeeping behave as the *payload* changes shape — the
fifteen real application trees the compression spike pinned
(`compression-spike/results/corpus.json`: the four benchmark applications,
six more open-source ones, five IT Tiger releases; 28,399 files, 3.6 GB,
from four files to twelve thousand and from 2 MB to 1 GB), plus the minimal
installers as the fixed-overhead anchor. Every application gets the same
deliberately small package, stated once in `packages/broad/contract.md` and
generated three times per application by `scripts/New-BroadPackages.ps1`:
install the canonical tree into the root the command line names, user
scope, Add/Remove Programs registration through the technology's own
mechanism, uninstall from the uninstaller it registered, nothing else. The
functional-contract packages of the first benchmark are not used.

```powershell
# 0. The product under test: the accepted 0.10.0 release binaries (cargo build --release);
#    the compression spike's payload trees must be present (compression-spike/README.md)

# 1. Enumerate and verify the corpus against the spike's evidence; write the per-file inventories
pwsh -File benchmark\scripts\New-BroadCorpus.ps1 -ResultsRoot benchmark\results\0.10.0-broad

# 2. Generate the package definitions from the corpus record (committed; the test checks they are current)
pwsh -File benchmark\scripts\New-BroadPackages.ps1 -CorpusJson benchmark\results\0.10.0-broad\corpus.json

# 3. The 48 builds (Minimal + 15 x 3), serial, under the meter; a small determinism check afterwards
pwsh -File benchmark\scripts\Build-Installers.ps1 -CorpusJson benchmark\results\0.10.0-broad\corpus.json -BroadPackagesRoot benchmark\packages\broad `
    -ArtifactsRoot benchmark\artifacts\0.10.0-broad -ResultsRoot benchmark\results\0.10.0-broad
pwsh -File benchmark\scripts\Test-BuildDeterminism.ps1 -Only minimal,notepadplusplus,gitforwindows

# 4. One smoke row per technology into a results root of its own, then the 45 rows
pwsh -File benchmark\scripts\Invoke-BroadBenchmarkLab.ps1 -OnlyRows TigerKeyring-NSIS,WinSCP-InnoSetup,NotepadPlusPlus-TigerSetup `
    -ResultsRoot benchmark\results\0.10.0-broad\smoke\lab -OutputJson benchmark\results\0.10.0-broad\smoke\lab-results.json `
    -BuildJson benchmark\results\0.10.0-broad\build.json -Fresh
pwsh -File benchmark\scripts\Invoke-BroadBenchmarkLab.ps1 -Fresh

# 5. The report and its CSVs; the focused checks of the machinery
pwsh -File benchmark\scripts\New-BroadReport.ps1
pwsh -File benchmark\scripts\Test-BenchmarkScripts.ps1
```

What is different from the campaigns above, and why:

- **The corpus is the spike's, verified, never re-derived.** `New-BroadCorpus.ps1`
  reads the spike's committed corpus and per-file inventories, checks every
  tree on disk against them (count, bytes, the (path, bytes) set; SHA-256
  where the first benchmark's inventories exist) and writes the campaign's
  own SHA-256 inventory of each tree for the rows to verify against. GIMP
  stays excluded with the spike's reason. One payload (TigerKeyring, decomposed
  from a shipped TigerSetup installer) carries that installer's packaged
  actions under `.tigersetup/`, a directory TigerSetup reserves and refuses
  in a payload: every package excludes it, in all three technologies, and the
  corpus record says so (`packageExcludes`); the corpus record itself is
  unchanged.
- **Uninstall runs what Add/Remove Programs registered.** A row reads the
  `UninstallString` the install wrote and starts that executable — Inno
  Setup's `{app}\unins000.exe`, NSIS's `$INSTDIR\Uninstall.exe`, TigerSetup's
  state-directory copy — rather than a path the driver assumed.
- **Package-owned state outside the root is part of the contract.**
  TigerSetup's state directory (`%LOCALAPPDATA%\TigerSetup\Benchmark.<App>`)
  is inventoried after install and must be gone after uninstall, and its
  removal is inside the uninstall clock (the uninstaller's helper deletes it
  after the engine exits: a hand-off, so it is timed like NSIS's `Au_.exe`).
  Inno Setup and NSIS keep nothing outside the root and the registry key;
  NSIS's `%TEMP%\~nsuA.tmp` (the uninstaller copy, marked for deletion at
  reboot) is recorded as residue, not counted against cleanup.
- **Rotation by index.** With fifteen applications the technology order
  cycles through three rotations in corpus order, for builds and rows alike,
  so each technology is first for five applications and last for five.
- **Distributions, not totals.** The report gives every per-application
  figure and then the median, quartiles, minimum and maximum over the
  fifteen, and counts (smaller, within ±5%, within ±10%, more than 10%
  larger; faster, slower) — a corpus of one gigabyte and one of two megabytes
  do not add.
- **Every row names the inventory that judged it.** A row records the
  canonical inventory its installed payload was compared with and that
  document's own SHA-256 (`canonicalInventory`), alongside the installer's
  hash and bytes. Twelve thousand file hashes per row are what the lab
  returned; what the campaign keeps is the verdict and its anchor — see
  *What a campaign commits* above.

## Local engine measurements (0.8.0 and 0.9.0)

Two measurements taken on the build machine rather than in the lab, because
they compare two engines on one machine and needed to be cheap to repeat.
Neither is the benchmark's number: `report.md` is the lab's, on the clean VM.

**`scripts/Measure-LocalUninstall.ps1`** generates three synthetic payloads
shaped like the applications the benchmark measured — 1,200 files of 450 KB
(ShareX-like), 38 files of 6 MB (qBittorrent-like), 60 files of 120 KB — builds
each with `--fast`, installs it per user, uninstalls it from the state
directory's uninstaller, and reports the wall clock and the engine's own span
(first to last log timestamp, which excludes the loader and the shell). The
`before` column is 0.7.1's transaction model with the 0.8.0 format; `after`
is 0.8.0.

| Shape | Install engine span | Uninstall engine span | Uninstall wall |
|---|---:|---:|---:|
| 1,200 × 450 KB (553 MB) | 12.18 s → **4.15 s** (2.93 s with the release profile below) | 19.94 s → **1.26 s** | 22.55 s → 1.91 s |
| 38 × 6 MB (240 MB) | 1.51 s → **0.95 s** | 1.96 s → **0.08 s** | 4.58 s → 0.79 s |
| 60 × 120 KB (7 MB) | 0.70 s → **0.20 s** | 0.98 s → **0.09 s** | 3.59 s → 0.82 s |

**The journal's batches as recovery units (0.8.0 → 0.9.0)** (the same
script, the 0.8.0 engine against the 0.9.0 one, seven repetitions each, the
median engine span and the range; the `journal_commits=` count the 0.9.0
engine's `transaction_committed` event reports, against the 0.8.0 engine's
count derived from its model — two commits per 256 operations of any kind —
and the 0.7.1 model's three per operation; a fresh database's eight schema
commits are included in every count):

| Shape | Install: commits 0.7.1 / 0.8.0 / 0.9.0 | Install engine span, 0.8.0 → 0.9.0 | Uninstall engine span, 0.8.0 → 0.9.0 |
|---|---:|---:|---:|
| 1,200 × 450 KB (553 MB) | ≈3,724 / ≈21 / 61 | 3.44 s → 3.41 s (3.31–3.84 → 3.13–3.80) | 1.41 s → 1.42 s |
| 38 × 6 MB (240 MB) | ≈178 / ≈13 / 43 | 0.49 s → 0.55–0.65 s (four of seven runs at 1.6 s under a scanner) | 0.08 s → 0.14 s |
| 60 × 120 KB (7 MB) | ≈250 / ≈13 / 29 | 0.17 s → 0.21–0.32 s | 0.09 s → 0.13 s |

The 0.9.0 engine journals a file batch by the builder's bound — 256
files or 32 MiB, so the 553 MB payload is 17 batches where 0.8.0's engine
took 5 — and a registry value, a PATH entry, an environment variable and a
firewall rule each on its own, with its previous state committed before its
own mutation (`TigerSetup-Design.md` §5.4). That is what the extra commits
are, and they cost about 3–5 ms each on this NVMe drive: nothing measurable
against the large payload's file work, 40–100 ms on the small transactions,
where the Add/Remove Programs registration's ten values are most of it. On a
slower drive each commit costs proportionally more; the count, not the
bytes, is the term to watch.

What the profile of 0.7.1's uninstall showed, in order of cost, and what
changed (`TigerSetup-Design.md` §5.4, §5.10):

1. **The plan hashed every owned file** to decide "modified → preserve": 553 MB
   read, and — because the files had just been written by the install — read
   through the real-time scanner, at about 74 MB/s. 0.8.0 records each file's
   size and last-write time with its hash and hashes only a file whose
   fingerprint changed: the plan takes 29 ms.
2. **The Restart Manager was given every file** the plan touches, and it opens
   each one to find its holders — the same scanner cost again (6.6 s once the
   plan no longer paid it). 0.8.0 probes each file with a `DELETE`-access open
   that reads no data and registers only what something holds: 0 ms for a
   product nobody has running.
3. **Three durable commits per operation** (`prepared`, `applying`, `applied`),
   about 2.3 ms each on this machine's SSD and several times that on a VM
   disk: 3,700 commits for 1,238 operations. 0.8.0 journals in batches of up
   to 256 operations — every undo record in one commit before any mutation,
   every `applied` in one commit after — so the same uninstall is about 12
   commits, with the invariant (undo durable before the mutation, the
   mutation durable before the record of it) unchanged.
4. **Every removed or replaced file was copied to the staging area and
   flushed** as its undo. 0.8.0 moves it there (`ReplaceFileW` for a
   replacement, a rename for a removal), so no bytes are copied; the staging
   directory is deleted once after the commit.
5. **The state-directory uninstaller's deletion helper inherited the caller's
   pipe**, so a caller reading the uninstall through a pipe waited two more
   seconds for `ping`. 0.8.0 starts it with no inherited handles.

**Release profile.** The audit behind `Cargo.toml`'s `[profile.release]`:
each row is the whole workspace built under one profile (fat LTO, one
codegen unit, `panic = "abort"`, stripped throughout), judged by the engine's
bytes after `zstd-19-w27` — what every installer carries — and by the engine
span of the 1,200-file install and uninstall above, plus `verify` of the
installed 553 MB (pure SHA-256 throughput, files warm in the cache). The
"Loader raw" column is the Rust loader of that audit; the C loader that
replaced it (below) is not built by the Rust profile and does not move with
it.

| Profile | Engine raw | Engine compressed | Loader raw | Install | Uninstall | Verify | Build |
|---|---:|---:|---:|---:|---:|---:|---:|
| `opt-level = "z"`, fat LTO | 2,593,792 | 1,221,796 | 539,648 | 4.32 s | 1.28 s | 1.75 s | 34 s |
| `"s"`, fat | 3,236,864 | 1,433,254 | 541,184 | 4.14 s | 1.32 s | 1.74 s | 40 s |
| `2`, fat | 3,731,968 | 1,599,885 | 567,808 | 3.20 s | 1.29 s | 0.84 s | 73 s |
| `3`, fat | 3,930,624 | 1,658,355 | 572,928 | 3.14 s | 1.29 s | 0.75 s | 56 s |
| `3`, thin LTO | 4,007,936 | 1,664,797 | 583,680 | 2.93 s | 1.39 s | 0.77 s | 69 s |
| **`"z"` with `sha2` and `zstd-*` at 3** (chosen) | 2,603,520 | 1,228,518 | 549,376 | **2.93 s** | 1.28 s | **0.74 s** | 37 s |

Only two loops are hot in an installation — SHA-256, which hashes every byte
written and every file verified, and the Zstandard decoder — and both live in
crates of their own, so those two are built at opt-level 3 and everything else
stays at z: the chosen row has the speed of the whole engine at 3 for 6.7 KB
more compressed bytes than z. Uninstall does not move with the profile: its
time is the filesystem's. The SQLite compile options declined in
`.cargo/config.toml` (extension loading, column metadata, STAT4, `soundex()`,
memory statistics, deprecated interfaces, progress callback, shared cache,
double-quoted string literals) took a further 56.8 KB raw and 27.3 KB
compressed off the engine on top of that row.

**Sizes that ship (0.8.0).** The loader block of a generated installer is
about 550 KB: the Rust runtime about 150 KB, the product icon about 100 KB,
the Zstandard decoder about 65 KB, the static CRT about 55 KB, the loader's
own code about 22 KB. The engine block is about 1.2 MB compressed (2.5 MB raw).
A generated installer therefore starts at about 1.75 MB before its payload,
against 2.5 MB for 0.7.1's uncompressed engine stub.

(`compression-spike/report.md`); the ZIP-era gap of 47–87% is gone. These
are sizes only: the lab campaign in `report.md` was not re-run for 0.8.0.

## 0.9.0 against the 0.8.0 baseline

0.8.0 was the first transaction optimization: the solid `zstd-19-w27`
payload, the Rust loader in front of a compressed engine, container format 2
with the Protocol Buffers metadata stored raw, and the batched journal. 0.9.0
keeps every architectural decision and changes what carries it: a C Win32
loader, container format 3 with the metadata compressed as one zstd block,
the builder's file batches as the journal's recovery unit, and durable
firewall and `HKLM` state (a rule in `SYSTEM` and the machine scope's values
are flushed to the disk before the journal calls them applied, where 0.8.0
flushed neither). The 0.8.0 figures are the ones recorded for that release
and are not regenerated; the 0.9.0 figures are the rebuilt final artifact's.

| | 0.8.0 (recorded) | 0.9.0 (final artifact) |
|---|---:|---:|
| Loader | 549,376 B (Rust) | 74,752 B (C) |
| Engine, compressed block | 1,201,641 B | 1,146,224 B |
| Engine, raw | 2,546,688 B | 2,489,344 B |
| Metadata block | raw protobuf, stored uncompressed | one zstd block (the self-installer: 18,633 B → 8,398 B) |
| Footer | 256 B, format 2 | 320 B, format 3 |
| Self-installer `TigerSetup-<version>-Setup.exe` | 3,647,738 B | 2,971,148 B |
| Fixed overhead before the payload | ≈1.75 MB | ≈1.22 MB |

The loader's own breakdown: 42 KB of code — the Zstandard decoder 28 KB
(one Huffman and one sequence decoder, no forced inlining, no assembly), the
loader's own code 10 KB, what the compiler needs of the C runtime 3.5 KB
(`memcpy`, `memset`, the `/GS` cookie; it starts at its own entry point,
hashes through CNG and allocates from the process heap) — 9 KB of read-only
data and 20 KB of resources (the 16 KB six-size 8-bit icon, the manifest
and the version block, which the builder replaces with the product's). The
ordinary `/MT` C runtime start-up would have made it 173,056 bytes. The
engine links the Zstandard decoder alone: the uninstaller copy's metadata
block is a stored frame no compressor writes. The journal measurements above
are the 0.8.0 → 0.9.0 A/B on the build machine; the lab rows for 0.9.0, and
the fresh build-resource comparison with Inno Setup and NSIS, are in
`report-0.9.0.md`.

## Design decisions worth knowing before extending this

- **Canonical payload rule.** For a given app, all three technologies install
  byte-identical application files. `New-CanonicalPayload.ps1` extracts the
  pinned artifact and records every normalization it performs (a zip's nested
  top-level folder flattened, ShareX's portable-mode marker removed, VLC's
  WiX/MSI build sources excluded, NSIS's `$PLUGINSDIR` and generated
  `uninst.exe` excluded from qBittorrent), so nothing is adjusted silently.
- **Functional contract.** Each app's `packages/<app>/contract.md` derives a
  common installer-level contract from the app's *real* upstream installer
  script, states every simplification, and is implemented by all three
  package definitions with every option defaulting to the upstream default.
  Each technology uses its natural primitive for each feature — a native
  primitive where it has one (a registry write is `[Registry]`,
  `WriteRegDWORD` and `[[registry]]` respectively), its script where it has
  not (PATH in Inno Setup and NSIS), a custom action where none of the three
  has a typed form (WinMerge's COM shell extension: `[Run]`/`[UninstallRun]`,
  `ExecWait`, `[[actions]]`). No technology is handed a deliberately awkward
  form where it has an equivalent primitive.
- **No hard-coded Windows paths.** A package definition never carries
  `C:\Windows\System32`: Inno Setup uses `{sys}`, NSIS runs tools by name,
  and TigerSetup's `kind = "exe"` action runs exactly the program it names
  (deterministic on purpose), so a Windows tool is run through a packaged
  one-line `.cmd` the command shell resolves (`winmerge/tigersetup/actions/`).
- **Version identity.** TigerSetup requires a strict `major.minor.patch`
  version; WinMerge's real version has a fourth component (`2.16.58.2`), so
  all three benchmark packages use `2.16.58` for identity parity.
- **Compression.** Production-quality settings for each technology: Inno Setup
  `lzma2/max` solid, NSIS `/SOLID lzma`, TigerSetup's release build (its
  normal compression search, never `--fast`).
- **Row lifecycle.** One lab session per row: the VM is restored to the
  `TigerWinLab-Win11-Clean` checkpoint, the install job runs, the uninstall
  job continues on the same VM, the session closes, and the driver waits for
  the lab to report the VM `Available` before the next row. Rows never share
  a VM or overlap. Technology order rotates between applications.
- **Timing boundaries.** Install: the installer process's lifetime. Uninstall:
  the uninstaller's lifetime plus the exit of the process it hands off to
  (an NSIS uninstaller copies itself to `%TEMP%\~nsuX.tmp\Au_.exe` and exits
  while the copy works) and the removal of the install root. The generic
  guest reader (`lab/guest/Invoke-SetupCommands.ps1`) implements both waits
  per command (`waitForProcesses`, `waitForAbsentPaths`); results record the
  process lifetime and the completion wait separately. There is no fixed
  sleep anywhere in the measured path. One measurement per row. A
  TigerSetup 0.9.0 installer is a loader that extracts its engine and waits
  for it, so its process lifetime spans the whole operation; the row still
  waits for any process of the installer's own name (the engine keeps the
  package's file name) on both install and uninstall, so a hand-off would
  show as completion wait rather than escape the clock — the boundary is
  the same, and the recorded wait says whether anything used it.
- **Contract probes are technology-neutral.** A file type counts as
  associated whether the installer set the extension's default (Inno Setup,
  NSIS) or registered a handler under `OpenWithProgids` (TigerSetup); a verb
  counts under the ProgID or under `SystemFileAssociations`; a scheme counts
  with its command under the scheme class or a handler ProgID. Every probe
  records the mechanism it found, so the report can say how each technology
  did it rather than score it.
- **Job account.** Every command runs as the lab's job account (`LabAdmin`,
  session 0, an administrator with no interactive desktop): every invocation
  here is silent. `regsvr32` therefore registers WinMerge's shell extension
  machine-wide in all three technologies, a property of COM registration
  rather than of any installer.
